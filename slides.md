# The choice at the start

<DecisionFork :step="$clicks" />

<!--
When this project started we had to choose.
A: convert the XSD and XML world automatically, as close as possible to the structural source. Risk: garbage in, garbage out.
B: build a true ontology of the conceptual world by hand, and map the XSD onto it. Risk: the RDF and the XML no longer conform to each other.
1 ERA asked the industry for feedback. Option A had the most support.
2 That has a consequence that runs through the rest of this talk: the ontology is as good as the XSD, plus what post-processing repairs.
-->

<PipelineFlow :step="$clicks" />

# A form becomes a dictionary

<XsdToRdf :step="$clicks" />

<!--
An XSD is a form template: which boxes, in which order, how often. An ontology is a dictionary of things.
1 A group of boxes becomes a class.
2 A box with a value becomes a property. "Exactly once" becomes a cardinality rule in SHACL, and a functional property in OWL.
3 minOccurs zero becomes optional.
4 The documentation becomes the definition. The label is generated by splitting the name, hence "Location ident".
Simplified, but this is the real type from the TAF TSI XSD and the real mapping rules.
-->

# The assumptions the converter makes

<div class="rosetta">

| In the XSD … | … the converter assumes | |
|---|---|---|
| an element's **name** | is the **concept's name**. The IRI comes from the name only, not from where it is used | 🟠 |
| an element with sub-elements | is a **class** | 🟢 |
| an element with a plain value | is a **datatype property** (a value) | 🟢 |
| an element pointing to a complex type | is an **object property** (a link to another thing) | 🟢 |
| `extension base="X"` | means **"is a kind of X"** (subclass) | 🟠 |
| `minOccurs` / `maxOccurs` | are **cardinality rules**; "max 1 everywhere" also makes it **functional** | 🟢 |
| an enumeration | is a **SKOS code list** | 🟢 |
| `xs:choice` | means **exactly one of** (`sh:xone`) | 🟢 |
| `xs:documentation` | is the **definition**; the label is the name split on capitals | 🟠 |
| one name under several parents | has **all those parents** as its domain | 🟠 |
| a property whose kind can't be found | is a **datatype property** by default | 🟠 |
| one name, once a value, once a link | gets a **DP / OP suffix** to keep the two apart | 🟠 |

</div>

<div v-click class="card warn-card mt-3">Every 🟠 row assumes the XSD author <b>named things after what they are</b>, used <b>one name per concept</b>, and used <b>extension only for "is a"</b>. XSDs are written to validate messages, not to describe the world.</div>

<!--
Green rows are safe: they follow from the XSD's own semantics.
Amber rows are guesses about the author's intention. They hold when the XSD is well designed. The next slides show what happens when they don't.
Source: xsd2rdf utils.py (create_property_iri_suffix, create_class_iri_suffix, create_formatted_label) and XSDtoRDF.py (generate_owl_graph).
-->

# One concept, three names

<SynonymNotes :step="$clicks" />

<!--
The same TAF XSD uses three element names for the name of a primary location. One of them doesn't even have a type.
1 The converter sees three different words, so it makes three different properties. All three are in v4.0.0.
2 Same story for the code itself.
No converter can fix this without a human deciding these are the same thing.
-->

# Names for roles, not for things

<RoleHub :step="$clicks" />

<!--
This is the key slide.
The XSD reuses one type, LocationIdent, for many elements, and names those elements after their role in a message: section from, section to, delay location, destination.
1 Post-processing renames LocationIdent to era:PrimaryLocation, to connect to RINF. Now 27 properties point to a primary location.
2 Five of them are about a track. The XSD documentation says so: "the track ID on which the train runs". In the ontology, a track is now a primary location.
3 The XSD also uses extension to reuse fields. The converter reads that as "is a". Is the origin of a journey section a kind of location, the way a station is? No. It's a location playing a role. The XSD never says that, so the converter can't know.
Link to agenda item 5, primary location attachment.
-->

# Same name, different meaning

<div class="grid grid-cols-2 gap-6 mt-4">
<div class="prob">

### 🧩 Different structure
`author` is a plain name in `Book`, but a whole `Person` in `Article`. One name, two kinds of property.

<div class="text-sm mt-2">The converter adds <code>DP</code> / <code>OP</code> to keep them apart. Post-processing turns real clashes into <code>…Value</code> and <code>…Reference</code>, for example <code>era:tariffValue</code> and <code>era:tariffReference</code>.</div>

<div class="text-xs muted mt-2">Example from the xsd2rdf README; tariff from v4.0.0.</div>

</div>
<div class="prob">

### 🎲 Different definitions
NeTEx declares `AccessModes` separately in **6 files**, each with its own documentation. They all collapse onto one property.

<div class="text-sm mt-2">Which definition wins changed between two runs on <b>identical input</b>: "Allowed MODEs to access SITE ELEMENT." in one, "MODEs of access which may used at associated place…" in the next.</div>

<div class="text-xs muted mt-2">xsd2rdf issue #27: 16 properties differ between runs.</div>

</div>
</div>

<div v-click class="card mt-6 text-lg">Same root cause every time: the converter takes the <b>name</b> as the <b>identity of the concept</b>. In a schema, a name only has to be unique in its context.</div>

<!--
Two quick ones. Both come from the same root cause: the name is taken as the identity of the concept.
-->

# NeTEx: an ontology written in a schema language

<NetexLadder :step="$clicks" />

<!--
NeTEx is kept as a separate bundle, for a reason. It is an extremely big XSD with a lot of abstraction in it: it tries to be an ontology, written in XSD.
The converter can handle it, but the result is a very strange ontology. Three quarters of the classes are schema plumbing: reference structures, relation structures, version structures.
1 The deepest "is a" chain runs over 14 levels of those structures.
2 And the real thing, Quay, has no superclass at all. Its fields live on Quay_VersionStructure.
NeTEx would need a lot of curation before it reads like an ontology. That is why it is not merged into the ERA namespace today.
-->

# Six steps after the converter

<PostProcessSteps :step="$clicks" />

<!--
All of this is in the telematics-ontology repository, run after xsd2rdf.
1 Each source is converted on its own, into the ERA namespace, with the technical suffixes on.
2 The rename list: this is where telematics meets RINF. LocationIdent becomes PrimaryLocation. Note: this is also what created the 27 arrows we saw.
3 The code lists get readable, stable names.
4 Every property gets the same annotations the ERA core uses: its code list and its validation rule.
5 The suffixes go, across all sources at once. A real clash becomes Value and Reference, and the step fails if any clash would remain.
6 Merge into two bundles, build the parameter-group tree for the app guide, and run the checks.
-->

# Three take-aways

<div class="grid grid-cols-3 gap-6 mt-8 text-left">
<div class="tk">🔁<br><b>The converter is a translator, not an analyst.</b><br>It is faithful to the XSD, including its inconsistencies. That was the choice, and it has a price.</div>
<div class="tk">🧠<br><b>Meaning has to be added by people.</b><br>The rename list is where that happens today. It covers 12 shared terms; the rest is still to discuss.</div>
<div class="tk">✍️<br><b>Better XSDs give a better ontology.</b><br>Name elements after what they are, one name per concept, extension only for "is a". Or curate on top.</div>
</div>

<!--
If the TSI XSDs get revised in the CCM process, these three rules make the next conversion much better.
